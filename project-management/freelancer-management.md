# Freelancer Management — Health Facility Locator

## Purpose

This document defines how the Health Facility Locator freelancer will be sourced, onboarded, managed and evaluated.

The objective is to ensure clear communication, controlled project scope, secure development practices and successful delivery.

---

## Freelancer Sourcing

The freelancer will initially be sourced through Fiverr.

Potential freelancers will be evaluated based on:

- Relevant Google Maps API experience
- Location-based application experience
- Frontend development experience
- API integration experience
- Git/GitHub experience
- Responsive web development experience
- Previous healthcare or health-tech projects
- Client reviews and ratings
- Portfolio quality
- Communication quality
- Understanding of the project requirements

---

## Fiverr Proposal Requirements

Each shortlisted freelancer should provide:

1. Relevant project examples.
2. Google Maps API experience.
3. Proposed technology stack.
4. Estimated development timeline.
5. Total development cost.
6. Expected third-party/API costs.
7. Testing approach.
8. API security approach.
9. Confirmation of GitHub experience.
10. Questions or assumptions about the project.

---

## Freelancer Selection Criteria

| Criteria | Weight |
|---|---:|
| Relevant technical experience | 25% |
| Google Maps/API experience | 20% |
| Portfolio and previous work | 15% |
| Communication | 15% |
| Git/GitHub experience | 10% |
| Timeline | 5% |
| Price/value | 10% |
| **Total** | **100%** |

Price should not be the only factor used to select a freelancer.

---

## Before Development Begins

The selected freelancer must:

- Review the project requirements.
- Review the user stories.
- Review the acceptance criteria.
- Review the sprint backlog.
- Confirm the proposed technical approach.
- Confirm the required Google APIs.
- Identify expected API or third-party costs.
- Confirm the estimated timeline.
- Confirm the development cost.
- Confirm how API keys and credentials will be handled.
- Confirm the GitHub workflow.

Any major assumptions should be documented before development begins.

---

## GitHub Workflow

The freelancer should work through the agreed GitHub repository.

Where appropriate, the freelancer should:

- Create a development branch.
- Make clear and descriptive commits.
- Keep changes organized.
- Reference relevant task IDs in commits.
- Avoid committing credentials or secrets.
- Push completed work to GitHub.
- Provide clear notes for significant technical changes.

The Product Manager will review submitted work before final acceptance.

---

## Communication

Primary communication will take place through the agreed Fiverr communication channel.

Important project decisions should be documented rather than relying only on informal messages.

Communication should cover:

- Progress updates
- Completed tasks
- Current tasks
- Blockers
- Technical questions
- Scope changes
- Expected delays
- Testing results

The freelancer should provide regular progress updates during development.

---

## Progress Tracking

Project progress will be tracked using:

- GitHub — development and task-related work
- Google Sheets — project tracking, budget, payments and deadlines
- Fiverr — freelancer communication and contract management

The Product Manager will use these tools to maintain visibility across the project.

---

## Payment Management

Payments should be linked to agreed project milestones where possible.

Example milestone structure:

| Milestone | Deliverable | Payment Status |
|---|---|---|
| Milestone 1 | Technical setup and Google Maps integration | Pending |
| Milestone 2 | Location search and facility discovery | Pending |
| Milestone 3 | Filtering and facility details | Pending |
| Milestone 4 | Directions, testing and responsive design | Pending |
| Milestone 5 | Final fixes and handover | Pending |

Final payment should only be released after agreed acceptance criteria have been met and required deliverables have been received.

---

## Scope Management

Any request that changes the agreed scope should be documented.

Examples of scope changes include:

- Adding new features.
- Adding new facility categories.
- Adding appointment booking.
- Adding user accounts.
- Adding reviews and ratings.
- Adding an administration portal.
- Changing the agreed technology approach.
- Significant changes to the user interface.

Scope changes should be evaluated for:

- Impact on timeline
- Impact on budget
- Technical complexity
- Impact on existing functionality

The Product Manager should approve significant scope changes before development begins.

---

## Testing and Quality Assurance

Before final acceptance, the freelancer should test:

- Current location functionality
- Manual location search
- Map display
- Facility markers
- Facility filtering
- Service filtering
- Facility details
- Directions
- Mobile responsiveness
- Desktop responsiveness
- Loading states
- Empty-result states
- Location permission denial
- API failure states
- Browser compatibility

Critical bugs must be resolved before final acceptance.

---

## Security Requirements

The freelancer must not:

- Commit API keys or passwords to GitHub.
- Share private credentials through public channels.
- Hard-code sensitive credentials into publicly accessible code.
- Expose unnecessary secrets in screenshots or documentation.

The freelancer must explain how Google API credentials will be protected.

---

## Final Handover

Before the project is considered complete, the freelancer must provide:

- Final source code.
- GitHub repository updates.
- Setup instructions.
- Google Maps/API configuration instructions.
- Required environment variable information.
- Testing notes.
- Known limitations.
- Technical documentation.
- List of outstanding issues, if any.
- Handover instructions.

The Product Manager will review the final implementation against the acceptance criteria before closing the project.

---

## Freelancer Performance Review

After completion, the freelancer should be evaluated on:

- Quality of delivered work
- Timeliness
- Communication
- Technical competence
- Ability to follow requirements
- Ability to respond to feedback
- Documentation quality
- Testing quality
- Adherence to security requirements

The outcome can inform future freelancer engagements.
